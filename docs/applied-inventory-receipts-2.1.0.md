# Applied inventory receipt boundary (development checkpoint)

Pinned26.2 ClientPacketListener.handleContainerSetSlot and handleContainerContent both return normally for ignored packet/container branches. A whole-handler TAIL callback alone therefore does not prove an inventory mutation. In particular, a late packet for an old container must not become fresh evidence for a disposal, material submission or recipe attempt.

The receipt Mixin now injects AFTER each of the two real write sites: InventoryMenu/AbstractContainerMenu.setItem for single slots, and their initializeContents invocations for a complete container. The same existing receipt observers run only after that write returns. Each handler pins require=2/allow=2 across the two distinct branches, so a missing/additional write-site injection fails rather than silently downgrading to a handler-tail observation. There is no packet cancellation, replacement, fabricated state, item move or network call. Existing same-thread/world/root/container/cursor/snapshot/epoch and workflow-specific receipt guards remain required; application evidence alone does not authorize an action.

The direct player-inventory packet has one unconditional native Inventory.setItem call; its existing TAIL plus canonical valid-slot mapping is unchanged. Cursor, server-close, movement and harvest packet hooks retain their separate scopes. No world/input/feature/settings behavior changes.

scripts/test-applied-inventory-hooks.py inspects the actual pinned vanilla class with javap, exhausts its normal-return branch graph and demonstrates both applied and ignored paths. It checks the narrow source hook and rejects unsafe before-write/count/target mutations. With --transformed it inspects an actual Mixin-exported ClientPacketListener.class from the isolated client: each applied branch must reach exactly one receipt callback after exactly one write, and ignored branches must reach zero receipt callbacks. This is bytecode control-flow verification, not a live-server or arbitrary packet-semantics proof. No retyped Java handler or synthetic success event stands in for the actual listener.

The smoke preparation export option KUANPERION_SMOKE_EXPORT_RECEIPTS=1 is test-only, default absent, and scoped to the isolated client directory/listener class. It does not change the production JAR, real game configuration or account. All unfinished feature and live validation release gates remain open; stable2.0.17 remains installed.
