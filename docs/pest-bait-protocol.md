# Pest bait transfer protocol — declared layout, not live support

## Evidence boundary

The supplied legacy PestTrapManager finds both bait material and the trap role using display-name substrings, performs two timed PICKUP clicks, then closes the menu without server cursor/quantity acknowledgement. Those operations were inspected for the requested behavior, not copied as authority. Official-domain public searches on2026-10-26 did not establish the current Trap Bait menu role/capacity/quantity schema. No search snippet is treated as a current live layout or successful refill.

This increment is a pure protocol plus abstract subtask, **not a native refill feature or a current-server compatibility claim**. Synthetic27-slot direct-item fixtures with an external bait slot13 have no asserted connection to the actual server. A server menu using a decorative counter instead of the declared direct material slot is unsupported until a separately verified native projection exists.

## Preconditions before any future native pickup/deposit

- Exact user-authorized raw bait ID, per-trap units and maximum source stack; defaults grant no consumption. Main inventory9..35 only, no hotbar/equipment/unique/protected items. All43 slots are frozen, not just bait stacks.
- Exact selected trap identity, current No Bait membership, current Pest root/world/Garden and actual native reach/interaction proof; no root or Farming hold is newly acquired by this subtask.
- Actual current menu identity and declared role, zero cost and **remaining capacity** must be independently proved by the native adapter, before both pickup and deposit. A left-click can transfer the whole carried stack: a requested amount is not a quantity cap. The protocol therefore requires authorized units to equal `min(source count, actual declared capacity)`; it does not split by wishful thinking.
- The future adapter must independently recheck all43 items, exact fresh server menu, actual physical/server cursor and current lease on the client thread immediately before each single guarded action. A returned structural ticket is data, not native click authority. The existing generic native empty-cursor guard is unchanged.

## Implemented pure sequence

1. Only a fresh applied source-empty receipt and exact full-stack carried receipt advance pickup to deposit. Client prediction alone cannot advance.
2. Only the exact declared material/count appearing in the direct target slot, backed by a newer target receipt and an exact physical/server remainder, advance deposit. Changed capacity/No Bait membership is rejected before the abstract port can send a deposit.
3. If there is a remainder, only that own server-proven remainder may return to the original still-empty source. Full43 revalidation and fresh cursor scope are repeated before arming; losing/resetting that scope revokes the earlier proof. Source restoration plus a new empty cursor must both be acknowledged.
4. Only a fresh disappearance of the same trap ID from the No Bait field, expected final inventory/material and physically/server-empty cursor confirm the operation. Settled evidence is revalidated before exact owned close. The parent retains its original Pest/Farming hold for later capture/return; this subtask never releases or re-arms it.

Manual/world/lease/menu/clock/timeout/unrelated inventory changes cancel or make the outcome uncertain. A rejected or ambiguous native result never retries, repairs a user's cursor, closes a taken-over GUI, buys supplies or claims completion. Unknown layout/capacity sends no transfer. If an operation is uncertain while an item is carried, the future parent must stop and tell the user; it cannot silently close or invent recovery authority.

## Remaining work

No production constructor caller, native role/capacity parser, carried-item action gate, parent Pest navigation/dispatch/cancellation integration, bait settings/UI, material purchasing or live test is introduced. Those require their own guarded implementation and current menu evidence. Existing Pest trap release/capture, all other features, installed2.0.17 and the user's settings are unchanged. Do not check off full bait replenishment or publish/install2.1.0 on the basis of these fixtures.
