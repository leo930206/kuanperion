# Settings entry / task coexistence checkpoint

The hotkey and local `/kuanperion` command share the actual guarded toggle. When a shared task is active, a non-inventory server container is still open, a carried item exists, or a loading overlay is present, opening settings is refused with local feedback. This is a read-only check: it does not close a menu, move an item, cancel a root, invalidate its Farming hold, send a command or queue an automatic later open. After ending the task and manually closing the container/returning the carried item, the user can request settings again.

Closing an already open MainGUI does not invoke the opening guard. With no new shared task, ordinary legacy Farming and Mining retain their existing non-pausing settings behavior. Title-screen local configuration remains possible. Command-only Stash does not acquire a shared gameplay root or server menu and is not newly blocked by this gate.

`scripts/test-settings-task-coexistence.py` compiles and executes the actual production toggle and read-only native gate with boundary fixtures, including all seven current shared-root owners, full cursor/container identity, overlay/thread, title and legacy context cases. Existing settings attack/pause/UI and typed native action tests remain required. These fixtures do not perform server interactions.

This is **not** the complete coexistence release gate. In-flight vanilla menu packets after an earlier cancelled command are not suppressed or fabricated as acknowledged. Per-feature manual requests made from inside settings, all delayed server responses and genuine server-menu transitions require further audit and live validation. No claim of uninterrupted new GUI workflows, automatic screen restoration or all-module completion follows from this checkpoint.

## Pest manual request follow-up

Pest's manual action now accepts one nonpersistent intent while settings is open, without acquiring a root, holding Farming, reading/replaying a flight target or touching a tool/input/menu. The existing native screen-null predicate is required before dispatch. The request expires after30 seconds and is bound to its original world and Farming armed-state; any observed blocker, unavailable context, another owner, stop/Jerry/world invalidation, disable or policy change clears it. No automatic reattempt follows a failed fresh task preflight. Queuing does not enable automatic Pest.

The real UI exposes pending status and the existing stop action while waiting. Closing settings starts at most one fresh bounded task with the original runtime's current target/tool/lease safeguards. `PestManualQueueTest` executes the actual task/session against native-boundary fixtures, and `UiModelTest` executes the actual queue/stop/visibility/status callbacks against compiled production UI classes without a world or native effects. Other manual-feature UI paths and delayed vanilla packets remain unchecked release work, not an implied extension of Pest's tests.

## Garden maintenance manual follow-up

Greenhouse, Composter and Visitor now use a small pure `ManualTaskRequest` intent ledger, explicitly requiring Garden, with the same30-second/world/Farming/blocker rules, before acquiring a task root or querying Visitor data. Each existing task performs its own full fresh preflight only after the native screen-null predicate permits dispatch. Policy changes, disabling, explicit cancellation and the existing manual/Jerry/world lifecycle hooks clear pending intent. A failed fresh preflight reports once instead of retrying or enabling automatic mode.

Three dedicated real-service/task/session tests cover waiting without effects, fresh one-shot dispatch with the original hold, duplicate/expiry/clock/world/Farming/blocker/policy/stop failures and lost flight permission. Compiled-production `UiModelTest` invokes all three actual manual/stop callbacks and checks pending visibility/status, no native/data calls, no ownership and byte-identical preference files. Existing automatic intervals/cooldowns, standalone eligibility, cancellation receipts, material safeguards and notifications remain in place. These are offline proofs, not live-server acceptance or completion of Trade manual paths/delayed vanilla responses.

## Trade manual follow-up

Auto Sell NPC and Junk now use the same transient intent ledger. Explicit constructor scope permits the NPC path in known SkyBlock (including standalone Hub) but keeps Junk Garden-only. The existing disposal feature context removes **only** the full-inventory blocker; every other blocker still revokes pending intent. Empty ID lists or an unconfigured Junk point do not queue a task. After settings closes, current source identity/protection, current Junk position, ownership and the actual task's existing limits are checked anew. Queuing never sends `/boostercookie`, opens inventory, disposes an item, holds Farming or enables/saves a job. Pending status and stop callbacks are available in both Trade modules.

The actual manual world-look, inventory-click and ordinary-command hooks now cancel pending Trade as well. For an already active Trade task, they revoke its session **before** calling Trade cancellation: otherwise an old task could close the server/inventory menu that the human has just taken over. `scripts/test-trade-manual-takeover.py` composes those actual production method bodies with real services/tasks/session and checks unchanged menu/item/cursor ownership on both inventory and command takeover. The trusted typed-command path still returns before manual cancellation, preserving the original Jerry behavior. Existing world/Jerry/legacy invalidation hooks already cancel both services.

Two additional real-service queue tests cover current scope, full inventory, deadlines, context and original Farm/world changes, policy/stop/Jerry revocation and fresh Junk position. Compiled-production UI models exercise both real manual/stop callbacks without native effects or preference changes. This closes these particular Trade manual-entry conflicts, not the current live NPC/Junk/packet compatibility or the whole upgrade gate.
